title: Security
description: Protect credentials and telemetry content
---

Keep provider keys and storage tokens in environment variables or a secret
manager; do not commit them to source control. The Elysia example reads
`OPENAI_API_KEY` and optional HTTP storage tokens from the environment.

Telemetry content capture is opt-in. Review the data sent to external model,
storage, and telemetry providers before enabling it in production.

## Authentication and tenants

For a multi-tenant service, pass an `AuthProvider` to `createApp()`. It must
verify the incoming request and return a principal with a subject ID, tenant
ID, optional workspace ID, and permissions. Lunar scopes saved runs, sessions,
workflow runs, and user memories to that identity. Workspace scope is carried
through the Elysia routes into storage adapters. Do not derive identity or
workspace from an unverified request header. Knowledge context is shared at
the configured tenant/workspace boundary; use a provider that applies document
ACLs when source records have user-level access rules.

`createDefaultApp()` requires an `AuthProvider` unless the caller explicitly
sets `allowUnauthenticated: true`. The packaged server accepts that opt-in
through `LUNAR_ALLOW_UNAUTHENTICATED=true` and binds to `127.0.0.1` by default.
Use an authenticated app when exposing the service through a public listener
or reverse proxy. HTTP run and workflow responses redact internal failure
messages; the runtime and persisted records retain them for operators.

`@lunar-adk/auth-better-auth` provides `createBetterAuthProvider()` for Better Auth
sessions. The application maps a verified Better Auth user/session to Lunar's
tenant and permission model. Curated memory endpoints require `memory:read`,
`memory:write`, or `memory:delete` permissions.

For Elysia, use `createAppWithBetterAuth(runtime, { betterAuth, mapPrincipal })`.
It mounts Better Auth's `/api/auth` handler and protects Lunar routes with the
same verified session.

By default, persisted sessions, runs, and workflow runs are private to the
principal that created them. If the host application supports shared resources,
provide `authorizeResource` to apply its ACLs for each operation. Lunar still
requires the resource tenant and workspace to match the authenticated principal;
the callback decides whether that principal may perform the requested action
inside that scope.

```ts
createApp(runtime, {
  auth,
  authorizeResource: ({ principal, resource, action, value }) =>
    kanoAccess.canPerform({
      userId: principal.subjectId,
      organizationId: value.tenantId,
      projectId: value.workspaceId,
      resource,
      action,
    }),
});
```

Keep project/task authorization in the host application. The callback can use
its membership and sharing tables; Lunar does not need to know Kano's domain
model.

## Credentials for tools

Authentication credentials for incoming requests and credentials an agent uses
to call another service are separate. Configure a host-owned `toolCredentials`
provider on `createRuntime()`. It receives the verified principal, tool name,
and a credential reference chosen by trusted tool code. The host must check
that the user can use that credential and requested scopes, then return a
short-lived access token. Lunar passes the principal only for the current
execution; it does not persist it with run, session, or workflow state. On
approval or workflow resume, authenticate the new request again.
For the packaged Elysia server, pass the same adapter as `toolCredentials` to
`createDefaultApp()`; for a custom Elysia app, configure it when creating the
runtime.

```ts
import { createRuntime, defineTool } from '@lunar-adk/adk';

const runtime = await createRuntime({
  toolCredentials: {
    async resolve({ principal, toolName, credentialId, scopes }) {
      // The app resolves a vault reference after checking membership and scopes.
      return credentialVault.accessToken({
        userId: principal.subjectId,
        tenantId: principal.tenantId,
        toolName,
        credentialId,
        scopes,
      });
    },
  },
});

const calendarTool = defineTool({
  name: 'calendar_list',
  description: 'List events from the connected calendar',
  schema: calendarInputSchema,
  async execute(input, context) {
    const credential = await context?.getCredential?.({
      credentialId: 'primary-calendar',
      scopes: ['calendar.events.read'],
    });
    if (!credential) throw new Error('Calendar is not connected');
    return calendarClient.list(input, {
      accessToken: credential.accessToken,
      tokenType: credential.tokenType,
    });
  },
});
```

Keep refresh tokens and provider secrets inside the host vault. Do not put them
in tool inputs, model messages, run outputs, events, or session state. A tool
should use a server-configured credential reference; the model must not choose
which user's credential to load. Direct `Agent.run()` calls do not receive a
runtime credential provider; configure the provider on `createRuntime()`.

For harnesses or Kano, the integration flow is: verify the host session, map
the verified user and tenant to `AuthPrincipal`, call Lunar with that
principal, let `authorizeResource` check the host's object ACL, and let the
credential provider authorize tool access against the same host identity.

## Request quotas

Pass `rateLimit` to `createApp()` (or `createAppWithBetterAuth()`) to enable
token-bucket request limits. The default app reads `RATE_LIMIT_MAX_REQUESTS`,
`RATE_LIMIT_WINDOW_MS`, and `RATE_LIMIT_TENANT_QUOTAS` from the environment;
see `apps/elysia/.env.example`. Authenticated requests are counted by verified
tenant ID; optional tenant-specific quotas override the default. The full quota
is available as a burst and replenishes evenly over `windowMs`. Health,
readiness, and auth-handler routes are exempt. Rejected requests return `429`
with `Retry-After` and `X-RateLimit-*` headers.

```ts
createApp(runtime, {
  auth,
  rateLimit: {
    windowMs: 60_000,
    maxRequests: 120,
    tenantQuotas: { "free-tier": 30, "enterprise": 600 },
  },
});
```

The default in-memory store bounds its active tenant entries, expires old
windows when it needs capacity, and returns `503` if it cannot safely track a
new tenant. Its counters reset on restart and are not shared across app
instances. For multiple instances, pass a `rateLimitStore` implementing
`RateLimitStore.consume()` with an atomic shared-store operation, or enforce
quotas at a shared gateway. Store failures return `503` rather than bypassing
the quota. When auth is not configured, all requests share one anonymous
quota bucket. Limits count HTTP requests equally; they are not token or cost
budgets.

## Runtime policy rules

Pass ordered `policyRules` to `createRuntime()` to allow or deny named agent
runs, workflow runs, and tool execution. The first matching rule wins; a rule
without `name` matches every target for its action, and unmatched actions are
allowed. Denied work fails with `POLICY_DENIED` before the model, workflow, or
tool body runs.

Plugins can add rules through `context.policies.register(rule)` during runtime
bootstrap. Application `policyRules` are evaluated first; plugin rules follow
plugin dependency order.

```ts
const runtime = await createRuntime({
  policyRules: [
    { id: "block-shell", effect: "deny", action: "tool.execute", name: "shell" },
    { id: "allow-tools", effect: "allow", action: "tool.execute" },
  ],
});
```

Rules apply to `RuntimeHandle` methods, including streams, workflow recovery,
workflow sub-agents, and resumed actions. They do not apply when calling an
`Agent` instance directly.
