---
title: "Use case: durable agent"
description: Recover long-running agent work across restarts
---

```ts
import { createRuntime, defineWorkflow } from '@lunar/adk';
import { createSqliteStores } from '@lunar/storage-sqlite';
```

Durability comes from pairing the runtime with persistent stores and making
long-running work resumable.

```ts
const storage = createSqliteStores('lunar.db');
const runtime = await createRuntime({ storage, ownsStorage: true });
```

Use normal agent runs for conversational turns. Use workflows for jobs that
contain multiple stages:

```ts
runtime.registerWorkflow(defineWorkflow({
  name: 'research',
  run: async (ctx) => {
    const previous = ctx.resumeFrom?.state;
    const result = previous?.output
      ? { output: String(previous.output) }
      : await ctx.runSubAgent('researcher', 'Collect the source material');

    await ctx.checkpoint('research-complete', { output: result.output });
    return result.output;
  },
}));
```

On restart, register the same workflow and call `runtime.recoverWorkflows()`
or load the workflow run by ID and call `resumeWorkflow()`. In the Elysia
service, `recoverWorkflowsOnStartup: true` resumes persisted runs with status
`running` before the app begins serving. Waiting-for-approval runs remain
paused. The latest checkpoint is exposed as `ctx.resumeFrom`; workflow code
should use it to avoid repeating completed stages. Give external side effects
their own idempotency keys because storage cannot undo an external operation.

Use a shared database adapter when deploying multiple service replicas so each
instance can load the same workflow, checkpoint, and session state. The
[Unknown Planet use case](/docs/use-cases/unknown-planet) shows the PostgreSQL
integration; other choices are listed in [persistence](/docs/guides/persistence).
