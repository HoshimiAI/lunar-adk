## Source-aware knowledge context

Lunar ADK owns execution and prompt construction. Unknown Planet owns ingestion,
scoped provider routing, retrieval, and source attribution. The Lunar adapter
uses a caller-supplied `Planet` client and never creates database clients,
installs database drivers, or runs Unknown Planet migrations.

Configure the Planet client with the capabilities your knowledge corpus uses,
then register its scoped context provider with the runtime. Agents opt in and
set their own retrieval limit:

```ts
import { createRuntime, defineAgent } from '@lunar-adk/adk';
import { createUnknownPlanetContextProvider } from '@lunar-adk/storage-unknown-planet';

const scope = { tenantId: 'acme', workspaceId: 'research' };
const context = createUnknownPlanetContextProvider({ planet, scope });
const runtime = await createRuntime({ context });
runtime.registerAgent(defineAgent({
  name: 'researcher',
  model,
  context: { providerId: context.id, retrieveLimit: 6 },
}));

const result = await runtime.run('researcher', 'What supports this claim?', {
  tenantId: scope.tenantId,
  workspaceId: scope.workspaceId,
});
const citations = result.run.events.find((event) => event.name === 'context.retrieved')?.payload;
```

Retrieved source text is marked as untrusted context and labeled in stable
result order (`[S1]`, `[S2]`, ...), with an instruction to cite those labels.
The `context.retrieved` run event stores the provider ID and source references,
including document title, content URI, and chunk offsets when Planet has them.
Retries reuse the same retrieved context; approval and continuation runs keep
the original labels and attribution. A tenant mismatch fails closed. If the
configured Planet client lacks queryable graph or chunk capabilities,
retrieval returns no context.

The Elysia example can opt in by passing `knowledgeContext: { planet, scope }`
to `createDefaultApp`; it does not run a database migration for retrieval.

## Optional run and workflow persistence

Use `@lunar-adk/storage-unknown-planet` when runs, sessions, and workflow state
must survive process restarts in PostgreSQL while remaining scoped to a Planet
tenant or workspace. The adapter uses PostgreSQL transactions and
revision-aware writes; its storage bundle atomically saves a run with its
session.

## Compose the adapters

When a service uses more than one Planet capability, create the adapters from
one client and scope. Select only the adapters the runtime needs:

```ts
import { createRuntime } from '@lunar-adk/adk';
import { createUnknownPlanetAdapters, migrateUnknownPlanetStorage } from '@lunar-adk/storage-unknown-planet';

const scope = { tenantId: 'acme', workspaceId: 'research' };
await migrateUnknownPlanetStorage({ planet }); // required only for SQL storage

const runtime = await createRuntime(createUnknownPlanetAdapters({
  planet,
  scope,
  storage: true,
  memory: { writeMode: 'persist' },
  context: true,
}));
```

The factory does not configure Planet providers, open connections, or run
migrations. Keep the Planet client and its providers application-owned.

## Create the storage bundle

Create a Planet client with its PostgreSQL SQL capability, run the additive
migration before serving traffic, and construct storage with the scope for the
authenticated tenant:

```ts
import { createRuntime } from '@lunar-adk/adk';
import {
  createUnknownPlanetStorage,
  migrateUnknownPlanetStorage,
} from '@lunar-adk/storage-unknown-planet';

await migrateUnknownPlanetStorage({ planet });
const storage = createUnknownPlanetStorage({
  planet,
  scope: { tenantId: 'acme', workspaceId: 'support' },
});
const runtime = await createRuntime({ storage });
```

The `planet` value above is an initialized `Planet` instance configured with a
PostgreSQL-backed SQL capability. The adapter applies the given scope to all
storage operations and rejects records whose tenant does not match it. Build
the storage bundle using the tenant authorized for the request; do not select
a tenant from untrusted request input. The caller owns the Planet client and
must close it after the runtime shuts down.

## Embedding ownership

When `MEMORY_PROVIDER=unknown-planet`, configure embeddings on the Planet
client itself. The adapter passes raw memory content to `planet.memory.add()`
and raw search text to `planet.memory.search()`. Planet's `PlanetConfig.embeddings`
provider creates vectors using its configured model and dimensions. Lunar ADK's
embedding provider remains independent and does not configure Planet.

With Unknown Planet SDK 1.1 or newer, set `unknownPlanet.memoryWriteMode` to
`"persist"` in `createApp` options when another system owns embeddings and graph
ingestion. This uses `planet.memory.persist()` and requires only Planet's memory
store; retrieval is lexical in this mode. The default `"ingest"` mode keeps
Planet-owned semantic ingestion.

For example, the OpenAI-compatible provider is configured when constructing
Planet alongside the PostgreSQL provider:

```ts
const dimensions = 1536;
const model = 'text-embedding-3-small';
const planet = new Planet({
  providers: [createPostgresProvider({
    database: pool,
    vectorCollections: { memory: { dimensions, model }, node: { dimensions, model } },
  })],
  routing: { memories: 'postgres', vector: 'postgres', graph: 'postgres' },
  embeddings: new OpenAICompatibleEmbeddingProvider({
    apiKey: process.env.OPENAI_API_KEY!, model, dimensions,
  }),
});
```

Apply Unknown Planet's PostgreSQL migrations with pgvector enabled. Keep the
embedding provider's model and dimensions aligned with each vector collection.
Lunar may use its own embedding provider for ADK-native memory; configuring it
does not implicitly configure this Planet client.

## Configure the Elysia example

The repository's Elysia app can create this adapter at startup:

```sh
STORAGE_PROVIDER=unknown-planet \
DATABASE_URL=postgres://user:password@localhost:5432/lunar \
PLANET_TENANT_ID=acme \
OPENAI_API_KEY=... \
bun run --cwd apps/elysia start
```

It runs the storage migration and scopes run, session, and workflow records to
`PLANET_TENANT_ID` (default `lunar-local`). For a multi-tenant service, use
application-managed per-tenant Planet scopes rather than sharing one fixed
tenant environment value across all users. `DATABASE_URL` is also used by the
optional PostgreSQL memory provider when `MEMORY_PROVIDER=postgres`; memory is
a separate capability and storage adapter.

## Verify persistence over HTTP

With the app running, check readiness, then create and inspect a run:

```sh
curl http://localhost:3000/readyz
curl -X POST http://localhost:3000/run \
  -H 'content-type: application/json' \
  -d '{"input":"Reply with unknown-planet-live-ok"}'
curl http://localhost:3000/runs/RUN_ID
curl http://localhost:3000/sessions/SESSION_ID
```

Use the returned session ID in a later `POST /run` request to continue the
conversation. The HTTP API's remaining run, session, workflow, and memory
routes are listed in the [HTTP reference](/docs/reference/http-api).

The migration creates `lunar.runs`, `lunar.sessions`, and
`lunar.workflow_runs`; it is safe to rerun. Keep those tables when rolling
back application code. Dropping them deletes durable application data and is a
separate operator decision. For an isolated local database and authenticated
live test harness, follow the [adapter README](https://github.com/HoshimiAI/lunar-adk/blob/main/packages/storage-unknown-planet/README.md).
